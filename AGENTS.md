# AGENTS.md — rules for every AI coding tool on this project

This is the single source of truth for Claude, Copilot, Cursor, ChatGPT, and any other AI tool.
If a human asks for something that conflicts with this file, point out the conflict and ask before doing it.

## Project
A wall-climbing robot built by a 5-person school team.
- **Firmware:** ESP32, PlatformIO, Arduino framework (C++), in `firmware/`.
- **Web UI:** React + Vite + TypeScript in `web/`. The ESP32 serves it (gzipped, from LittleFS) and the
  phone/laptop controls the robot over a **WebSocket at `/ws`**. Works with no internet: the robot is a WiFi
  Access Point `WallBot` → `http://192.168.4.1` (optional station mode + `http://wallbot.local`).

Hardware is still being decided. Unknown things are marked `TODO(hardware)`. **Never invent hardware details**
(pins, part numbers, voltages, I2C addresses). If you need one, ask or leave a `TODO(hardware)`.

## Hardware and config
- All pins, tunable constants, and network settings live in **one file**: [firmware/include/config.h](firmware/include/config.h).
  `PIN_NOT_SET` (-1) = not decided; code must skip that hardware, not crash. Never hard-code pins or tuning values.
- Private WiFi credentials go in `firmware/include/secrets.h` (git-ignored), never in committed files.
- Arduino-ESP32 core **2.0.17** (PlatformIO `espressif32 @ 7.1.3`). Use 2.x APIs, e.g. `ledcSetup()` +
  `ledcAttachPin()`, **not** 3.x `ledcAttach()`.

## Architecture (firmware)
- **Control task** (core 1, every 10 ms, `main.cpp`): sensors → state machine → adhesion + wheels → telemetry.
- **Comms task** (core 0, `src/comms/`): WiFi, web server, WebSocket. **Only comms touches networking.**
- They exchange data **only through `shared_state.h`** (lock-protected copies). WebSocket callbacks must
  **never** call motor/adhesion/sensor functions directly.
- **No `delay()`** in the control task or any `...Update()`/`set...()` function. No blocking loops, no waiting.
- State machine (`state_machine.h`, pure C++ and unit-tested): `ESTOP` (latched, boot state), `LINK_LOST`, `RUNNING`.

## Module interfaces (shared, do not break)
The `.h` files in `firmware/include/` are the contract. Read their comments for units and ranges.
- **locomotion.h**: `locomotionInit()`, `setMotorSpeed(int leftPct, int rightPct)` (-100..100, clamped), `stopMotors()`
- **adhesion.h**: `adhesionInit()`, `adhesionUpdate()`, `adhesionSetPower(int pct)` (0..100), `adhesionGetPower()`, `adhesionIsOk()`
- **sensors.h**: `sensorsInit()`, `sensorsUpdate()`, `SensorData sensorsGet()` (every reading has a `...Valid` flag)
- **comms.h**: `commsStart()`
- **protocol**: [docs/protocol.md](docs/protocol.md). Firmware parser `src/comms/protocol.cpp`; web types `web/src/protocol.ts`.

Rules:
- Don't rename/remove/change parameters of anything in a `.h` file without the lead's OK, and **say so
  explicitly** in your answer and the PR ("This PR changes a shared interface").
- Adding a new field to `SensorData` is allowed; mention it in the PR.
- Protocol changes: update `docs/protocol.md`, `protocol.h`, `protocol.cpp`, `protocol.ts` **together**;
  bump `PROTOCOL_VERSION` in both code files if old clients would break. Lead approval required.

## Build, upload, test
Run from the repo root unless noted. Full steps in [README.md](README.md).

| What | Command |
|---|---|
| Web dev server (laptop on robot WiFi) | `cd web && npm ci && npm run dev` (set `VITE_ROBOT_WS_URL`, see `web/.env.example`) |
| Build web into `firmware/data` | `node scripts/build-web.mjs` |
| Upload web UI to the robot | `cd firmware && pio run -t uploadfs` ("Upload Filesystem Image") |
| Build / upload firmware | `cd firmware && pio run` / `pio run -t upload` |
| Serial monitor | `cd firmware && pio device monitor` |
| PC unit tests | `cd firmware && pio test -e native` |

- Web changes need **build-web + uploadfs**; firmware changes need **upload**. Forgetting uploadfs is the most
  common mistake; the UI shows a version mismatch when it happens.
- CI builds web + firmware + filesystem image and runs the PC tests on every PR. Red CI = can't merge.
- New library (firmware `lib_deps` or web `package.json`)? Ask the lead first; pin exact versions for firmware.
  Keep the web UI small: no UI kits or chart libraries.

## Coding style
- **C++:** 2-space indent, braces on the same line. Functions `camelCase` prefixed with the module
  (`sensorsUpdate`); constants `UPPER_SNAKE_CASE`; file-local things `static`. Include headers by name
  (`#include "config.h"`). `config.h`, `protocol.*`, `state_machine.*` must not include `Arduino.h` (PC tests).
- **TypeScript/React:** function components + hooks, strict TypeScript, no `any`. Components in
  `web/src/components/`. Only `useRobot.ts` talks to the WebSocket.
- Put units in names: `distanceMm`, `timeoutMs`, `speedPct`, `pitchDeg`, `batteryV`.
- Keep functions short. Comment *why*, not *what*. Remove your `TODO` when you finish it.

## Safety rules (mandatory, see SAFETY.md)
- **Link-loss failsafe:** the UI sends `drive` or `heartbeat` every ~100 ms. No message for `LINK_TIMEOUT_MS`
  (500 ms) → **wheels stop, adhesion keeps running**. Cutting adhesion on the wall makes the robot fall.
- **E-STOP** is latched in firmware until an explicit `reset_estop`. The UI's E-STOP button is big and always visible.
- Firmware **clamps every incoming value** and limits wheel power to `MAX_MOTOR_POWER_PCT`.
- The UI must show connection status clearly and **turn red when disconnected**.
- Never remove or weaken any of the above, or change safety constants, without the lead's explicit OK.
- When unsure, fail safe: `adhesionIsOk()` → `false`, missing sensor → `Valid = false`, wheels stop.
- The UI is **not** a replacement for the physical kill switch.

## Git rules for AI tools
1. Work only on a feature branch (`feature/...` or `fix/...`). **Never commit to `main`.** Never force-push.
2. Small, focused changes: one task per branch/PR. Don't reformat or "clean up" unrelated code.
3. Only edit your own area (table above) unless the human explicitly tells you otherwise.
4. Never change pins, `config.h` safety values, shared interfaces, or the protocol silently. If you do,
   say so explicitly in your answer and in the PR description.
5. Make sure it builds (`pio run`, `npm run build`) before suggesting a commit.
6. Commit messages start with the area: `locomotion: add PWM setup for left motor`, `web: add joystick`.
7. No secrets in the repo (WiFi passwords, keys).
8. Explain your changes so the student understands them: they must be able to explain the code in review.
